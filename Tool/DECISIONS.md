## D1 · 2026-10-19 22:46 · `hotthread.mjs` v1 → v2：机会分从"根评论赞数"改成"楼内回复战绩"

**证据（同一晚的天然对照）**

| 楼 | 根评论赞 | 楼内回复赞数 | 说明 |
|---|---|---|---|
| `BV1wenJ65EFG` root=317558392545 | 264 | 16 / 11 / 7 | 楼里回复能拿两位数 |
| `BV1VMJi6GErN` root=317400656849 | 555 | 几乎无人回复 | 根评赞最高，但回复全在 1 赞 |

v1 的公式 `root_like / (rcount + 1)` 把"楼内回复多"当坏事——**方向反了**。真正的因果是：
**楼内回复真的拿到赞，才证明这个楼会把曝光分给回复**；根评论赞数只代表"这个楼有多显眼"。

**决策**：v2 用四个信号，全部来自接口、无一处靠猜

```
traffic   = view / age_hours                                      // 仍在被观看的速度
freshness = clamp(traffic / 5000, 0.2, 1.5)
proof     = reply_median*2.5 + reply_max*0.8 + reply_ge10*3       // 楼内战绩（主信号）
exposure  = root_like * 0.35                                      // 根评论能借出的曝光
slot      = 1 / (1 + 0.5*max(0, rcount+1-3))                       // 抢不到前 3 条就衰减
opportunity = (exposure + proof + 1) * freshness * slot
```

排序变化（同一批候选，仅换公式）：`BV16MJY6yEKq` 的 287 赞楼（楼内 23/20/6/0）从第 3 升到第 1（56 分 → 74.9 分）；
`BV1MmJX6SEZY` 的 190 赞楼楼内战绩最强（中位 20.5、最高 72），但视频只剩 895 播放/小时，
`freshness ×0.2` 把分数从 27 砍到 12.4（名次仍是第 8）——**流量已经过去的楼，战绩再好也吃不到**。

**代价**：每楼多 1 次 `/x/v2/reply/reply` 请求（硬门槛先过滤，实测 18 个候选只用 35 次请求）；
`freshness` 用生命周期平均速度，"曾经很热但正在冷却"的视频会被低估——这是已知偏差，不是 bug。

**回滚**：`Tool\bili\hotthread.mjs` 文件头公式段 + `signals` 字段都在；`git checkout` 该文件即可回到 v1。

## D3 · 2026-10-19 22:49 · `ledger.mjs` 增加归因标签：`add --style/--thread-size` + 新命令 `label`

**证据**：7 条评论、3 个赞（当时）却没有一个结构化标签，"什么样的评论能拿赞"无法回答；
`proven.ndjson` 资产库也因为无法归类而空着。

**决策**

- `add` 增加可选 `--style short-punch|long-arg|question|info`、`--thread-size <根评论赞数>`；
- 新增 `label --rpid <id> [--style] [--thread-size] [--at]`：**只补标签，不取网络、不动赞数历史**；
- `report` 每条输出 `style / thread_size / age_hours / like_per_hour`，并在人读表里显示 `[style]`。

回填 7 条后立刻可读出的第一份归因（n=7，样本极小，只作方向参考）：
`short-punch 3 条 4 赞` vs `long-arg 4 条 0 赞`。

**代价**：标签由人或 LLM 判定，不是客观量；因此它**只能用于规划，不能进入判定**。

## D4 · 2026-10-19 22:49 · 事件语义修正：`add` = 登记/重置，`label` = 补标签（**不改 audit.mjs**）

**经过（含一次走错路，必须记录）**

1. 首次实现时，我把 `derive()` 里 `add` 改成"重复 add 只合并标签、不重置"，想让回填更安全。
2. 结果 `audit.mjs` 立刻报 **FAIL**：`台账 sum_like 与事件日志一致 — 派生=0 汇总=3`。
   原因：audit 逐事件独立重放，遇到 `add` 就把该 rpid 清空；我的合并语义与它不一致。
3. 当时的两个选项：
   - **改 audit 的重放逻辑去迎合 ledger** —— 否决。audit 是"检查器"，让检查器跟着被检查者改，等于自证；
   - **改事件语义** —— 采纳：`add` 保持"重置"不变（audit 不动），新增 `label` 事件承载标签回填。
4. 副作用：回填用的 7 次重复 `add` 已经把赞数历史清空、并把 `posted_at` 改成回填时刻。
   修复方式：`sync` 重放赞数（恢复为 0/1/0/1/0/0/2），再用 `label --at` 把 `posted_at`
   逐条改回 **comments.ndjson 中首次 add 事件记录的原始时间**（16:00 / 16:40 / 17:06 / 17:11 / 17:49 / 17:50 / 22:33）。
   `audit` 复跑 **21 项全部通过**。

**决策**：`add` 用于首次登记（重复 add 会打印警告并建议改用 `label`）；`label` 用于补标签/纠时间。
**原则**：**检查器不迁就被检查者**。若未来再遇 audit 与 ledger 不一致，先问"哪一侧的语义更接近事实"，而不是"哪侧更容易过"。

**回滚**：三个文件的改动彼此独立（`ledger.mjs` 的 derive/label、`audit.mjs` 未动）。

1. **"楼内前 3 条才吃得到曝光" → 放宽到前 4 位**：第 4 位实测 7.58 赞/小时，没有断崖。
   位置仍然重要（同梗系里第 1 位是 21 赞、第 4 位是 5 赞），但不是"第 4 条就废"。
2. **"根评论 20–80 赞是甜区"（我 23:00 前的提议）→ 作废**：330 赞的楼照样给 7.58 赞/小时。
   真正的分水岭是**楼在不在爆炸期**，不是根评论已有多高。

**决策**（v3）

- `SLOT_FULL` 3 → **4**（前 4 位不吃位置惩罚）；
- `freshness` 主信号换成**根评论增速** `explosion`：
  - 优先 `root_velocity`＝两次快照差分（瞬时）；
  - 没有快照时用 `root_like / root_age_hours`（均值）兜底；
  - 都没有才退回原来的 `view/age_hours`；

**这正是"楼已验证会火、位置还没被占满"的窗口，6 小时前我完全抓不到这种目标。**

**代价**：`root_velocity` 需要至少两次运行才有差分值，首轮只有均值兜底；均值对"评论发布很久但一直慢慢涨"的楼偏高。

**回滚**：公式常量集中在 `hotthread.mjs` 顶部（`SLOT_FULL` / `BLAST_FULL` / `MIN_ROOT_VEL`），单行可调。

## D12 · 2026-10-19 23:40 · 修 `audit.mjs` 的窗口边界（**不放宽严格性**）

**问题**：`audit.mjs` 用 `derived.size === ledger.comments_in_window` 比对。`ledger.mjs` 只统计**窗口内发布**的评论，
一旦出现窗口外补登（例如 10-25 之后补登、或把上周评论也登记进台账），派生数会大于窗口内条数 → **audit 误报 FAIL，并宣称"判定数据不可信"**。

**决策**：把独立派生也按 `ledger.window` 过滤后再比对条数与总和，比较口径与 `ledger.mjs` 对齐。
这不是放水：仍要求"事件日志重放出来的窗口内条数、总和"与台账**逐项相等**，只是把比较范围改成同一口径。
输出里额外打印"事件共 N 条，窗口外 M 条"，让口径差异可见。

**代价**：若有人把评论 `posted_at` 改成窗口内来虚增统计，audit 不再能仅凭条数发现（但它也不曾能发现手改 `set --like`）。
**回滚**：`git checkout HEAD -- Tool/bili/audit.mjs`。

## D13 · 2026-10-19 23:40 · `hotthread.mjs`：覆盖保护 + 候选池混龄过滤

**问题（实测发生）**：23:25 我用 `--bvid BV1ZLJd6MEfo` 做单视频验证，把 23:24 那次 **18 视频 / 10 目标**的扫描结果
**覆盖成 1 视频 / 3 目标**。这与 `Tool.md §9.3` 里 `hunt` 的"空结果覆盖"是同一类缺陷。
另：`hotthread` 会读 `candidates_cold.json` / `candidates_niche.json`，其中是 17:xx 的旧快照，白跑请求。

**决策**

## D14 · 2026-10-19 23:50 · 新增"必须人工授权的工具"契约（`Tool.md §12`，提出人：用户）

**背景**：`Tool\git\push.ps1` 是唯一会**越过工作目录边界**的动作——它用真人账号的凭据把提交发布到 GitHub，

**决策**（`Tool.md §12`）

- 三步授权流程：说明影响 → 取得当前对话里的**明确同意** → 执行后留痕（结果、远端分支、commit 号）；
- 授权粒度：**一事一授权**，默认不跨会话继承；用户明确放宽后仍要每次报告结果；
- 清单当前只有 `Tool\git\push.ps1`；重试沿用同一次授权，但**换远端/换分支/强推必须重新授权**；
- 明确"不在清单里"的：`sensor` / `ledger`（含 `report`/`list`/`sync`）/ `audit` / `hunt` / `hotthread` / `proven`
  —— 只读公开接口、只写 `History\`、可重跑；`ledger add/set/label` 记录的是已发生事实，不改外部世界；
- 发评论本就不在脚本层（§9.1），不进清单。

**代价**：每次推送多等一次确认，慢一步；换来的是"以真人身份对外发布"这件事不会由代理单方面决定。
